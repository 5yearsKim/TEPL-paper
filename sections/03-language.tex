\section{High-Level Language Design}
\label{sec:language}
\subsection{Dialects, Operations, and Rewrite Rules}
\label{sec:dialects}
A dialect defines a reusable set of operations, including their operand
signatures, attributes, and semantics. Attributes configure operations independently of tensor values:
a transpose, for example, carries \code{permutation: index[]}.
The semantics of each operation can be described using Axes IR, introduced
in Section~\ref{sec:axes-ir}.

Rules import dialects using an \code{import} statement and use their
operations to describe tensor rewrites. A rule has the form \code{LHS => RHS},
with each side represented as an s-expression.

An operation node can be named using \code{:}. For example,
\code{(d: dot x y)} names the dot node \code{d}. This name can be referenced
in \code{derive} and \code{where} blocks.

\subsection{Attribute Binding and Transformation}
\label{sec:binding}
\begin{figuretext}[0.9]{figures/Attribute Binding and Derivation.pdf}{Captured operation attributes can be read in \code{where} and \code{derive} blocks. The \code{derive} block explicitly defines RHS attribute transformation logic using these captured attributes.}{fig:attribute-binding}{An input graph with transpose and dot is replaced by a dot. Colored descriptor
bindings connect the rule to a table with two captured rows and one derived row.}
LHS operation attributes are captured automatically at match time. Naming an operation
makes its descriptor accessible as \code{node.attrs}. For example,
\code{tr.attrs.permutation} selects the permutation of a named transpose
node \code{tr}.

Users can compute RHS attributes in a \code{derive} block by assigning a
descriptor to a named RHS node's \code{attrs} property, such as
\code{out.attrs}. Bracket notation provides syntactic sugar for directly
assigning an existing descriptor: \code{(dot[d.attrs] A B)} reuses
\code{d.attrs} for the RHS dot. Descriptor compatibility is checked
separately from rewrite correctness.

at match time and RHS attributes are derived from them using user-written
transformation logic.

Although our mathematical synthesis algorithm is complete for the defined
fragment, TEPL may still be unable to verify a rewrite with explicit
attribute derivations. Failure to verify a rewrite does not necessarily
mean that it is incorrect.

\subsection{Conditions with \texorpdfstring{\code{where}}{where}}
\label{sec:where}
Some rewrite rules are applicable only under specific conditions. A
\code{where} block expresses these conditions as predicates combined with
\code{&&} and \code{||}.

For operations with declared semantics, TEPL accepts a rule only when it can
establish that the RHS attributes are computable and produce a legal,
equivalent replacement under the \code{where} condition. For the mathematical
fragment, the LHS and RHS determine a feasibility predicate
$\operatorname{check}(p)$ (Section~\ref{sec:find}). The \code{where} condition
must imply this predicate for every legal LHS match.

For example, the following dot reassociation rule preserves the inner dot's
batch axes, assuming arithmetic that permits reassociation:
\begin{codeblock}[H]
\begin{lstlisting}[language=TEPL]
rule reassociate {
  (source: dot (inner: dot A B) C) => (dot A (dot B C))
  where {
    source.attrs.lhs_batching_dimensions == inner.axes.B.positions
  }
}
\end{lstlisting}
\end{codeblock}
The condition requires the outer dot's left batch dimensions to match the
inner dot's batch output positions in the same order.

When verification fails, TEPL can suggest an additional sufficient condition
to add to \code{where}. The user adds the condition and checks the rule again
(Section~\ref{sec:condition-suggestions}).

\subsection{Explicit Attribute Derivation with \texorpdfstring{\code{derive}}{derive}}
A \code{derive} block defines RHS attribute transformation logic using
captured LHS attributes. The following rule composes two transposes by
using \code{gather} to compose their permutations:
\begin{codeblock}[H]
\begin{lstlisting}[language=TEPL]
rule compose_transposes_explicit {
  (outer: transpose (inner: transpose X)) => (combined: transpose X)
  derive {
    combined.attrs = {
      permutation: gather(inner.attrs.permutation, outer.attrs.permutation)
    };
  }
}
\end{lstlisting}
\end{codeblock}
When applying the rule, this derivation computes the attributes of the
replacement transpose from the two captured permutations.

\subsection{Automatic Attribute Inference}
\label{sec:auto}
When RHS attributes are omitted and no derivation is provided, TEPL asks the
compiler to infer their transformation logic. The same transpose rewrite
can therefore be written without a \code{derive} block:
\begin{codeblock}[H]
\begin{lstlisting}[language=TEPL]
rule compose_transposes_auto {
  (transpose (transpose X)) => (transpose X)
}
\end{lstlisting}
\end{codeblock}

For transpose composition, the compiler infers the same permutation
transformation as the explicit derivation above. It constructs a reusable
function of source metadata rather than attributes for one fixed shape.
Runtime evaluates this function for each match. Unsupported inference
produces a diagnostic.
