\section{Introduction}
\label{sec:introduction}
\subsection{Motivation}
Algebraic tensor rewrites are widely used to improve execution efficiency in tensor
compilers. Production systems such as XLA and TVM use graph transformations
to simplify computations and enable efficient execution~\cite{xla-hlo-passes,tvm}.
Prior work uses algebraic transformations for graph
optimization~\cite{taso,tensat,spores}, distributed training~\cite{unity},
operator fusion~\cite{dnnfusion,neptune}, and optimization across
execution levels~\cite{mirage,trinity}.

Although tensor rewrite rules can be simple in algebraic form, they can
require substantial implementation logic. For example,
consider the dot reassociation rule, $(XY)Z \Rightarrow X(YZ)$. The equation shows how to
rearrange the computation, but general tensor dot operations also need
attributes specifying their batch and contraction dimensions. The rewrite
must compute how these attributes are transformed from the left-hand side (LHS)
to the right-hand side (RHS). For example, in XLA, this single transformation is implemented by the
\code{AssociativeReorderNestedDot} routine in 269 nonblank lines of C++ code
(excluding comments)~\cite{xla-simplifier}, including logic for attribute transformation and
checking applicability. This illustrates the substantial implementation complexity
hidden behind a seemingly simple algebraic rewrite rule.

A key difficulty is that matching the LHS does not determine the
attributes needed on the RHS. Users must therefore write
additional expressions or custom code to compute them. This requires
tracking how dimension positions, operand pairings,
and output order change across composed operations. Two dimensions with the same
extent can still represent different coordinates, so extents alone are not enough
to determine their correspondence. The transformation must also work for
tensors of arbitrary rank; checking a few fixed-rank examples does not
establish that it works in general.

Our research question is: \emph{What if we could design a language that makes
tensor rewriting as easy and intuitive as writing its algebraic form, while
leaving complex attribute transformation to the compiler?}
TEPL pursues this goal by using operation semantics and symbolic axis mapping
to infer RHS axis attributes under explicit conditions.
Figure~\ref{fig:why-tepl} illustrates the idea with a dot reassociation example.
TEPL lets users write rewrite rules in simple algebraic form and provides tools for
explicitly deriving attribute transformations. For eligible axis fields,
the compiler can infer these transformations automatically.

\subsection{Contributions}
\begin{enumerate}
\item \textbf{A practical language design for tensor rewriting.}
TEPL provides syntactic structures and tools for expressing tensor
rewrite rules concisely and intuitively.
\item \textbf{Automatic attribute inference.}
For supported rewrites, the compiler constructs reusable functions that
compute missing RHS axis fields from source metadata while preserving
supplied extent and coordinate attributes. Mixed explicit/inferred axis
fields use validation or certified schemas, with no completeness guarantee.
\item \textbf{Symbolic axis mapping for composed operations.}
We propose an algorithm that maps symbolic axis groups across composed
operations using operation semantics, enabling attribute matching for
input tensors of arbitrary rank.
\item \textbf{Correctness and completeness guarantees for a defined fragment.}
We prove constructive completeness for independent, fully unknown RHS axis
fields in read-once contraction, permutation, and unary summation, with a
restricted additive extension, exact arithmetic, and input extents at least
two. A shared symbolic metadata program realizes this constructor; a sufficient guard
checker establishes the end-to-end acceptance guarantee in
Theorem~\ref{thm:accepted-core}. Sound view/reindexing schemas add
broadcast and reverse; core validation also covers supplied fields.
Table~\ref{tab:guarantee-map} collects the guarantees and their scope.
These are paper proofs, not mechanized verification. We trust
operation declarations, frontend lowering, the C++ implementation of
checking/loading and primitive reasoning/evaluation, and backend agreement
with declared algebraic semantics.
\end{enumerate}
