\section{Introduction}
\label{sec:introduction}
The same tensor operation can be more efficient depending on how it is expressed.
Consider dot reassociation, $(AB)C \Rightarrow A(BC)$. The two expressions are
algebraically equivalent but have different computation costs. Suppose
$A\in\mathbb R^{100\times1}$, $B\in\mathbb R^{1\times100}$, and
$C\in\mathbb R^{100\times1}$.
Then $(AB)C$ requires 100 times as many scalar multiplications as $A(BC)$
($100\cdot1\cdot100+100\cdot100\cdot1=20{,}000$ versus
$1\cdot100\cdot1+100\cdot1\cdot1=200$).

This is why algebraic tensor rewrites are widely used to improve efficiency in tensor
compilers. For example, XLA, TVM, use graph transformations
to simplify computations and enable efficient execution~\cite{xla-hlo-passes,tvm}.
Other tensor compiler frameworks also highly rely on algebraic tensor rewrites for
graph optimization~\cite{taso,tensat,spores,pytorch2}, distributed
training~\cite{unity}, operator fusion~\cite{dnnfusion,neptune},
and optimization across execution levels~\cite{mirage,trinity}.

Although tensor rewrites are simple in algebraic form, their implementations
can be much more complex. For the simple dot reassociation rule above, XLA
implements this single transformation in the
\code{AssociativeReorderNestedDot} routine using 269 nonblank lines of C++
code (excluding comments)~\cite{xla-simplifier}.
How come a simple rule such as $(AB)C \Rightarrow A(BC)$ becomes this complex?

Many tensor operations carry attributes that specify operation metadata.
For the rank-two tensor example above, the dot operation on $A$ and $B$
maps tensors with axes $[i,k]$ and $[k,j]$ to a tensor with axes $[i,j]$.
Here, $k$ is contracted in both operands, requiring
\code{lhs_contract_dim=[1]} and \code{rhs_contract_dim=[0]}.
For a general dot operation on tensors of arbitrary rank, the contraction
dimensions can be multiple and noncontiguous. For example, given
$A\in\mathbb{R}^{i_1\times k_1\times k_2\times i_2}$ and
$B\in\mathbb{R}^{k_1\times j_1\times k_2}$, contracting $k_1$ and $k_2$
requires \code{lhs_contract_dim=[1,2]} and
\code{rhs_contract_dim=[0,2]}, producing
$AB\in\mathbb{R}^{i_1\times i_2\times j_1}$.
Dot operations can also specify batch dimensions. Thus, a general dot
operation has four axis attributes:
\code{lhs_contract_dim}, \code{rhs_contract_dim},
\code{lhs_batch_dim}, and \code{rhs_batch_dim},
each represented as a list of integers.

Much of the complexity of tensor rewriting comes from transforming these
attributes. Consider dot reassociation again. The left-hand side (LHS)
contains two dot operations, each with its own attributes.
Can the right-hand side (RHS) operations simply copy the LHS attributes?
No, this doesn't work in general.

Consider the dot reassociation rule $(AB)C \Rightarrow A(BC)$, where each
multiplication denotes a general dot operation. Let $A$, $B$, and $C$ have
shapes $[2,3]$, $[4,3]$, and $[4,5]$, respectively.
On the LHS, the first dot contracts dimension 1 of both $A$
and $B$, requiring \code{lhs_contract_dim=[1]} and
\code{rhs_contract_dim=[1]}. After reassociation, however, the first dot
operates on $B$ and $C$ and must contract dimension 0 of both operands.
Its contraction attributes must therefore change to \code{[0]} and
\code{[0]}. Even a simple algebraic reassociation cannot generally reuse
the original operation attributes. The compiler must explicitly derive new
contraction dimensions from the axis correspondence between the original
and rewritten expressions.

The example above uses rank-two tensors, but general dot operations must
also handle tensors of arbitrary rank, with multiple contraction and batch
dimensions. To implement the rewrite, users must track how these dimensions
move and pair across operations, then compute the RHS attributes.
Dimension sizes alone cannot guide this process: two dimensions can have
the same size but play different roles in the computation.
The attribute transformation must therefore follow the correspondence
between axes and remain valid across all supported ranks and dimension
configurations.

The core design philosophy of TEPL starts from this complexity.
How can we design a DSL dedicated to tensor rewriting with syntax as
intuitive as algebraic tensor expressions? How can it also help users
explicitly derive attribute transformations?

This leads to our research question: \emph{Beyond explicit attribute
derivation, can the compiler infer complex axis attribute transformations
automatically? Can it generate attribute transformation logic once at
compile time for tensors of arbitrary rank, then reuse that logic at
runtime with the given tensor metadata?}
Figure~\ref{fig:why-tepl} illustrates these two ways of expressing dot
reassociation and compares them with a handwritten implementation.

\begin{enumerate}
\item \textbf{A practical language design for tensor rewriting.}
TEPL combines algebraic rewrite rules, applicability conditions, and
explicit attribute transformations in one language.
\item \textbf{Automatic attribute inference.}
For supported rewrite patterns, TEPL derives missing RHS axis attributes
from operation semantics and match metadata, reducing the need for
handwritten attribute transformations.
\item \textbf{Symbolic axis mapping for composed operations.}
We introduce Axes IR and an algorithm that tracks symbolic axis groups
across composed operations. The compiler uses these mappings to generate
reusable feasibility checks and attribute builders for tensors of
arbitrary rank.
\item \textbf{Correctness and completeness guarantees for a defined fragment.}
Under the stated assumptions and exact arithmetic, we prove that attribute
synthesis constructs valid RHS axis assignments whenever they exist
within the defined fragment. Table~\ref{tab:guarantee-map} summarizes the
scope and assumptions of these guarantees.
